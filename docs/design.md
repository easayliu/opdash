# 页面设计说明

本文记录 opdash 各页面「为什么这样设计」。页面的功能清单见 [README](../README.md#页面)；查询层的实现与实测数据见 [queries.md](queries.md)。

## 首页：服务总览

首页参照 Cloudflare 控制台的 Zone Overview 设计，打开后首先回答「现在哪个服务不对」。整体遵循先总后分、注意力分层的原则。

* **顶部是全站指标**：全站请求量与错误率（各带变化）、异常服务数、进程重启次数，以及叠加了对比时段灰影的全站请求趋势。
* **异常的放大，正常的压缩**：错误率 ≥ 1% 或 P95 达到对比时段 1.5 倍以上的服务以大卡片置顶。卡片上多出一行**主因**（如「主要是 `GET /x`：P95 80ms → 2.1s」；只对异常服务查询一次接口表，挑选方法与服务详情页的变化榜相同）和**重启标记**（`↻ 2 次重启`，悬停可查看时刻与 pod）。其余八十多个服务每个一行，依次为名称、请求量、错误率、P95 与迷你趋势，一屏即可看完全站。悬停任意一行会出现三个图标，分别跳转到日志、链路与指标。
* **对比基线可选，默认为昨天同时段**：若与「上一小时」相比，白天的数据总在上涨、夜间总在下降，早高峰的自然爬坡会被误判为 +60%。接口为 `/api/services?compare=day|week|prev`，对比窗口整体平移，迷你趋势中的灰影也取自对比窗口。
* **样本充足时才按比例判定 P95**：两个窗口都至少有 300 次请求才做比较（`MIN_SAMPLES`）。低流量服务的几条慢请求就能抬高 P95，这是统计噪声而非故障。加入这条规则之前，首页的 6 个「异常」服务全部是每小时仅几百到几千次请求的服务；加入之后只剩 1 个，而且确属异常（对比时段零错误，当前开始出错）。
* **无意义的 P95 不显示**：入口 span 几乎不耗时（如消息确认类，P95 < 1ms）的服务，延迟一栏显示「—」并附说明，以免显示成 `4.1µs −5%` 而被误认为缺陷。

服务卡片上的三项内容：

* **三个指标各带对比**：请求量、错误率、P95 旁边标出与对比时段的变化（`+12%`、`3.1×`；错误数从零变为非零时标「新增」）。`/api/services` 一次返回当前窗口与对比窗口（`prev`），后端四条查询并发执行（当前窗口、对比窗口及两者的迷你趋势），线上 84 个服务一次往返约 1 秒。
* **迷你趋势**：30 格请求量柱图，错误以红色叠在顶部，对比时段的同一格以灰影垫底。比较两者的形状，便能判断「这个时段本来如此」还是「今天有所不同」。最后一格若不完整则不绘制（与全站图表的规则一致）。
* **健康色**（`ui/src/lib/health.ts`，全站共用一套阈值）：错误率 ≥ 5% 为红、≥ 1% 为黄；P95 ≥ 200ms 且达到上一周期的 3 倍为红、1.5 倍为黄；上一周期零错误而本周期开始出错也标黄。异常服务排在最前，点击顶部的「异常 N」只看这些服务。

## 服务详情：哪些接口变了

总览页回答「哪个服务不对」，服务详情页回答下一个问题：**哪个接口不对**。「这个服务比昨天慢 3 倍」无从着手，「`POST /order/submit` 的 P95 从 120ms 变为 2.1s，这一小时多耗了 34 秒」才可以据此行动。

因此接口表对当前窗口和对比窗口**各查询一次**（`/api/services/{name}/operations?compare=day|week|prev|none`，两条并发，均锁定 `service_name` 以使用排序键前缀，第二条的代价与第一条相当），再按 `(span_name, span_kind)` 对齐为一行。

每个服务最多保留 200 个接口（`LIMIT 200 BY service_name`，在排序之后截断，保留的是请求量最大的接口）。`span_name` 的基数不可控：把 SQL 语句、表名拼进 span 名的服务，`kind=client` 下一小时就有上千个名称，一次查询 24 个服务、再乘以两个窗口，就是数万行 JSON 和同样数量的 `quantilesTDigest` 状态。被截断的服务在响应中带 `truncated=true`，页面标注「接口已截断」，「接口消失」一档也会跳过它（排不进前 200 不等于接口消失）。

* **变化榜**（`ui/src/lib/compare.ts`）：在一屏之内指出变化的是哪几个接口。**按影响面排序，而非按百分比**：一小时 20 次的接口从 10ms 变为 40ms 是 +300%，会排在「5 万次的接口从 80ms 变为 120ms」之前，但使用者关心的是后者。所以先按性质分档（接口消失 > 错误增多 > 变慢 > 新出现 > 流量变化），档内按各自的影响面排序：错误看多出的失败次数，延迟看多耗的总时间（ΔP95 × 次数），流量看多出的请求次数。阈值思路与总览页相同（两侧各 ≥ 100 次才比较 P95，倍数与绝对值都须达到），低流量接口的统计噪声不会上榜。点击一行，上方两张图只显示这个接口。
* **接口表每一列都带变化**：次数、错误、错误率、P50、P95、P99 下方一行是相对对比时段的 `+12%`、`3.1×`。表头默认按数值排序，切换到「按变化排序」后按该列的变化排序。排查退化时，「P95 最高的」与「P95 涨幅最大的」往往不是同一批：前者本来就慢，后者才是今天新出现的问题。
* **接口的出现与消失**：只比较两侧都有的接口，会漏掉最明确的两类变化。对比窗口有而当前窗口一次都没有的接口，补一行 0 次并标「已消失」；反之标「新」（多半是新版本改了路由或 span 名）。
* **两张图也叠加对比时段**：请求量柱图背后垫一层灰影，延迟图多一条虚线「P95 · 昨天同时段」。选中某个接口后，对比线也只属于该接口，「从什么时候开始与昨天不同」一目了然。
* **对比基线随导航保留**：在总览页选择「与上周同时段比较」后，进入服务详情仍与上周比较（`serviceHref` 携带 `cmp`，见 `ui/src/lib/links.ts`）。

## 指标看板

* **Top 表 + 整页过滤**：按接口、下游地址、topic 的请求量画成 Top 表（每行一根占比条），而不是十二色堆叠柱。**点击一行，整页所有图表（包括顶部的数字与跳转链接）都按它过滤**，顶部出现可移除的标签。过滤条件放在 URL 的 `attr` 参数中，与「全部指标」共用，切换页签不会丢失。
* **重启与发布标记**（`/api/metrics/events`）：依据两个信号。一是累积 counter **回落**（`cur < prev`，只有进程重启才会如此，用于识别原地重启）；二是 **pod 在窗口内首次出现**（滚动发布时新 pod 从零开始、旧 pod 消失，任何一条曲线都不会下降，只能依靠这一信号）。使用 `jvm.cpu.time` 这类无标签的 counter 最为干净，按 `(service, k8s.pod.name)` 分区。标记绘制为虚线竖线，顶部一行列出时刻与 pod。线上验证过：某服务 24 小时内重启两次，P99 在第二条虚线前冲到 10 秒——先劣化、后被重启，二者恰好对应。
* **吸顶分区目录**：HTTP 服务端、客户端、JVM、连接池、Kafka 等分区组成一条横向目录吸附在顶部，滚动到哪一节就高亮哪一节，点击直接跳转。
* **面板由语义约定生成，而非固定列表**：面板定义在 `ui/src/lib/dashboards.ts`，每个面板给出一串候选指标名，取该服务实际上报的第一个；一个都没有则整块不显示。线上同时运行着两代 SDK，同一含义有两个名称（`http.server.request.duration` 以秒为单位、`http.server.duration` 以毫秒为单位；`jvm.*` 与 `process.runtime.jvm.*`），标签名也随之不同（`http.response.status_code` 与 `http.status_code`），候选列表用于消化这些差异；非 Java 服务再退回 collector 的 spanmetrics（`calls` / `duration`）。实测 `ai-crm` 生成 20 个面板、`eci`（旧 SDK）16 个、`job-center`（只有 HTTP 与 JVM）11 个。
* **面板进入视口后才发起查询**：一屏二十个面板同时查询，会一次占满后端的查询名额（`--max-concurrent-queries`，默认 16），其他人只能排队，集群也白白扫描了没人翻到的面板。单个面板的查询很轻（单服务、单指标、一小时：直方图分位数 0.015 GB / 0.3 s，gauge 0.001 GB / 0.05 s）。

## 图表的绘制规则

* **图形随数据性质而定**，观感与 Cloudflare 控制台一致：**计数与速率画堆叠柱**（按状态码、接口、GC 名称堆叠，构成一目了然，与服务详情页的「请求量与错误」一致）；**水位与分位数画折线**，只有一条线时在线下填充 12% 的浅色。图例可点击，点一下隐藏对应曲线，便于在按接口分组、十几条线挤在一起时只看其中一两条。
* **每条曲线都必须可辨认**：调色板只有 8 种可分辨的颜色（`SERIES_SLOTS`），第 9 条起都会落到同一种灰色，画出来也无法区分。因此，**堆叠柱**多取几条，第 9 条以后合并为一条灰色的「其他 N 条」（堆叠本就是看构成，合并并不失真）；**折线**不能合并（几条延迟曲线相加没有意义），只取前 8 条，图例上注明「还有更多」，需要全看时点击标题进入「全部指标」拆分查看。图例默认占两行（同一排卡片才能对齐），放不下的收为「+N 条」按钮，点击后展开全部，卡片随之变高。不允许出现画了却没有名称的曲线。
* **同一看板共用一根十字线**：鼠标停在任意一张图上，同屏所有图表都在同一时刻画出竖线（提示框只出现在鼠标所在的图上）。「GC 与延迟尖峰是否同时发生」无需来回对照横轴。
* **横向拖选即缩小时间范围**（与日志页直方图的交互一致）：拖选后整块看板按新范围重新查询，顶部「最慢的链路 / 出错的链路 / 错误日志 / 服务概览」等入口携带的也是这一段。在指标上看到尖峰，两步即可跳到那一分钟的链路与日志。服务详情页也有返回指标看板的入口。
* **丢弃最后一个不完整的桶**：时间范围的右端就是「现在」，最后一格往往只过了几秒，速率与计数只统计了一小部分。若不丢弃，每张图的末尾都会下跌一截，图例读数（最后一个值）也随之偏小，容易被误读为流量下降。
* **版式**：看板每行两列（两张宽图比三张窄图易读），面板数为奇数时最后一张占满整行，不留半行空白；图例固定两行高度，同一排卡片才能对齐；图例只写**有区分度**的标签（按接口查看 P95 时每条线都带 `quantile=p95`，写出来既占位置又没有信息量）。

## 页面之间的跳转

各页面之间的跳转表见 [README](../README.md#页面之间的跳转)。地址统一在 `ui/src/lib/links.ts` 中拼装：分散在各页面手写，迟早会有一处漏带 `from` / `to`。

### 返回目标不进 URL

链路详情是四条路径的共同终点（错误分组、链路检索、日志行中的 trace id、指标图上的 exemplar），因此返回目标不能写死。跳转时用 react-router 的 `state` 携带来源，详情页左上角显示「← 错误」或「← 日志」。

返回目标之所以**不进 URL**，是因为它属于这一次导航的上下文，而非视图状态。放进 URL 会随链接被复制给同事，对方点击后会跳到一个从未去过的列表。这也恰好给出了正确的显示条件：直接粘贴 URL 打开的页面没有来源，就不显示返回按钮，这比给一个猜测出来的目标更好。

### push 与 replace

**展开、选中这类瞬时状态修改 URL 时一律使用 `replace`，只有「切换了所看的对象」才使用 `push`。** 错误分组的展开以前使用 push，浏览列表时展开五组，就要按五次后退才能离开。

### 点选下钻

只携带服务与时间，到了新页面还得重新筛选一遍，而面板本身掌握着更多信息。点击图上的一个点，弹层中的链接会同时携带三项信息：

* **这一格的时间窗**（那一分钟，而非整个页面的时间范围）；
* **所点曲线的标签**，按语义约定翻译为目标页能识别的筛选条件：`http.route`、`http.response.status_code`、`server.address` 在 span 上是同名属性，直接转为链路页的 `attr=k=v`；`span.name` 转为 `span_name`；spanmetrics 的 `status.code=STATUS_CODE_ERROR` 转为「只看错误」；`res:k8s.pod.name` 转为日志页的 `pod` 维度筛选（对照表在 `ui/src/lib/links.ts`）；
* **该点的数值**：延迟类指标（单位为 `s`、`ms`、`us`、`ns`）额外给出一条「≥ 2.27s 的链路」，即 `min_ms`，从「P95 在这一分钟是 2.27 秒」直接跳到「这一分钟内慢于 2.27 秒的请求」。

**弹层打开时会查询一次这一格的报错**（锁定服务的一分钟窗口，线上 49 ms / 0.2 MB）：有报错则多一条「这一格的报错 · N 种」（悬停可查看前三种）；没有则直接说明「这一格没有报错，尖峰来自耗时而非错误」。**这句话本身就是答案**：它表明尖峰是慢而不是错，不必再去翻错误页。

之所以先查询、而不是直接给出链接，是因为错误很稀疏，直接给链接多半会打开一个空页面。线上测量过：对**出现过错误的**服务，随机点中的一分钟能命中错误的概率只有 10.9%。也不能靠放宽窗口弥补：前后各放宽 30 分钟也只到 39.8%（错误本身稀疏且成簇出现），却破坏了这个弹层「只看这一格」的约定，其余几条链接都精确到那一分钟。

### 从一个时刻跳到一段时间

从「一个时刻」（一条日志、一个 span、一个 exemplar）跳到按时间段查看的页面时，前后各放宽 15 分钟（`WINDOW_AROUND_MS`）。只给那一毫秒，指标图上一个点都没有；放宽之后才能看出尖峰从何时开始。

按 trace id 或 span id 查询日志时同样带时间范围，原因见 [queries.md](queries.md#按-trace-id--span-id-查日志要带时间范围)。

## 收藏查询

收藏的内容就是页面地址（路径 + 查询串）。页面状态本就全部在 URL 中，无须为每种筛选另写一套序列化，新增的筛选参数也自动可以收藏。

保存时去掉翻页位置和**时间范围**（`range` / `from` / `to`）：收藏的是查询条件，时间范围跟随顶栏。顶栏的范围本就跨页面共享，打开一条收藏时使用的正是顶栏当前的范围。点击的收藏恰好就是当前页面时，地址不变，按「刷新」处理，重新查询一次。

链路详情对应一条具体的 trace，30 天后即过期，不属于查询，因此不能收藏。
